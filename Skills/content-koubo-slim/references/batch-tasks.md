# 多篇口播任务

当用户要多篇独立稿件时读取。仍用现有五个 Skill；每篇沿用方向、正文、配套与保存三个确认点，批次只负责逐篇安排和进度。

## 理解需求

- 明确要“出10版口播”时，识别为10个独立稿件，不把数量放进 `must_keep`，不改成一篇含十个段落的长稿。不同角度可直接根据原要求安排，在方向阶段展示给用户。
- “把这篇改到第10版”是单篇修订；“给10个标题”是配套要求，不是10篇正文。按完整语义判断，不能按数字或“版”字机械路由。
- 明确只要多个方向或候选选一时，先展示候选并让用户选定，不自动把全部候选写成成稿。只有用途实质不明才问一个简短问题；不要新增固定问卷或确认点。
- 批次范围、共用选题、来源与讲述者必须一致。不同客户/知识库/IP分开批次，不能把一份 Context 在不同客户间复用。

## 内部执行

1. 首次为批次生成一次 UUID，在宿主任务工作目录持久保存计划；重试与恢复复用原计划，不重新生成编号。客户只看“第几篇、什么角度”，不必填写 UUID、item_id 或计划文件。
2. 调用既有 `start`，显式传 `--output-count N --batch-plan 计划文件`，其余 binding/Profile/topic/reference 参数与单篇相同。计划示例：

```json
{
  "batch_id": "工具生成并持久保存的UUID",
  "output_count": 2,
  "items": [
    {"item_id": "item-01", "user_thoughts": "从观众最担心的问题切入"},
    {"item_id": "item-02", "user_thoughts": "从一个具体任务和操作过程切入"}
  ]
}
```

3. 返回每项独立 `task_record`；分别读取对应 Analyzer 输入、生成方向、装配 Context、写稿及生成配套。不把第一项的稿子、确认或配套当作其他项的结果。每项的修改继续原 Run，`draft_version` 只表示该篇的修订次数。
4. 可以在同轮集中展示多篇同阶段的产物，逐篇标号并完整展示，随即结束本轮。只有下一条真人消息明确确认已展示的全部或指定篇目，才对这些项分别调用既有 `respond-*`；不对尚未展示、被要求修改或仍待确认的篇目代填决定。集中展示不减少每篇的确认约束。
5. 不同项可处于不同阶段。用户只改第三篇时，只重开第三篇，其他篇的确认和文件保持不变。某项失败保留已完成项并准确报告，修复后恢复原项；不新建整批绕开错误。
6. 保存后用 `batch-status --batch-id 原UUID` 核对进度。只有返回所有项的文件均已核验保存，才能说整批已保存；生成正文、通过结构检查或个别项保存，都不能代替整批完成。发现文件被移动、改写或丢失时报告实际差异，不重写覆盖用户文件。

批次参数或绑定变化时程序会阻断；需要重做范围时说明新旧任务关系并保留旧成果，不能偷偷给相同批次换客户、来源或篇目。文件保存使用篇目身份区分同名稿件；旧单篇任务的身份与命名保持兼容。

## 与客户沟通

方向阶段说明每篇角度及已拆解的参考；后续展示各篇正文和对应配套。进度可写“10篇中，6篇正文待确认，4篇已保存”。只引用程序返回的真实状态和路径；不声称已经替客户录制、发布或同步到平台。
