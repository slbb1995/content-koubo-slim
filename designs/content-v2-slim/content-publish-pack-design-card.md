# `content-publish-pack` Skill 设计卡

## 名称

- Skill 名称：`content-publish-pack`
- 用户语言名称：配套文案生成

## 唯一目的

在同一 Run 的口播正文已经真人确认后，只根据这份已确认正文生成、修改并交给用户确认 2 个封面标题、3 个发布标题、推荐项、50—100 字发布正文和 5 个标签。

本 Skill 只生成配套文案。它不创建 Run、不读取 Vault、不修改或重复输出正文、不调用旧标题/分发 Skill 或 Reviewer、不保存、不发布，也不进入 P6。

## 何时使用 / 何时不得使用

### 使用

- 当前 Run 状态为 `draft_approved`，且 `approved_draft.json` 精确绑定当前最终正文；
- 程序已经回读并确认同版本 `draft_vN.json` 与 `draft_vN.md` 一致；
- 首版只接收已确认正文；修改版额外接收当前 `package_vN` 和本次真人修改意见；
- 用户需要一次看到完整标题、发布正文和标签候选。

### 不得使用

- 正文尚未确认，正文版本或 JSON/Markdown 不一致；
- 需要改变原题、方向、客户、讲述者、正文事实或正文措辞；
- 需要搜索 Vault、参考件、网络、历史稿或其他客户资料；
- 需要调用旧 `viral-headline-creator`、`content-distribution-pack`、`content-save`、Reviewer、发布平台或 Git；
- 需要保存、上传、发布、生成数字人或进入 P6。

## 唯一输入 / 唯一输出

### 唯一正式输入：已确认正文

程序只提供已确认版本号和完整正文。修改时再提供当前配套版本和本次具体真人意见；不形成第二份正文、第二层 Pack、Schema 或任务句柄。

Skill 必须把正文当作只读事实边界：标题、发布正文和标签只能包装正文已经表达的判断，不得补造客户业务、产品、案例、数据、身份、承诺、CTA 或热点。

### AI 唯一输出：配套文案对象

```json
{
  "cover_titles": ["封面标题一", "封面标题二"],
  "publish_titles": ["发布标题一", "发布标题二", "发布标题三"],
  "recommended_cover_title": "封面标题一",
  "recommended_publish_title": "发布标题一",
  "publish_copy": "50—100 字发布正文",
  "tags": ["#标签一", "#标签二", "#标签三", "#标签四", "#标签五"]
}
```

AI 不输出正文、版本号、哈希、状态、审核说明、保存路径或发布信息。程序校验后 create-only 保存 `package_vN.json`。

## 配套生成规则

- 封面标题恰好 2 个，方向有区别，单独放在画面上也能让人知道主题对象、问题或冲突；不要写“干货分享、值得收藏、先问清几件事”等空泛流程句；
- 发布标题恰好 3 个，围绕同一正文主判断，从问题、误区、判断或人群场景中选择不同角度；
- 封面标题和发布标题各推荐 1 个，推荐值必须来自当前候选；推荐只是默认采用项，不代替真人确认；
- 发布正文为 50—100 字，只概括正文已有价值，不增加正文没有的事实、身份、承诺或行动要求；
- 标签恰好 5 个，互不重复，服务同一主题，不借热点或人名扩大事实范围；
- 不使用夸大收益、绝对承诺、恐吓、羞辱、假稀缺、倒计时或无依据数字；
- 标题与发布正文不得逐句搬运参考来源的识别性表达；本 Skill 看不到参考全文，不声称完成版权审核；
- 修改只解决本次真人意见，不趁机改变正文或另起一套内容方向。

## AI 职责 / 程序职责

### AI 职责

- 从已确认正文提取目标观众、主题对象、核心判断和可点击冲突；
- 生成数量固定、彼此有区别且全部能回指正文的配套候选；
- 理解用户对当前配套的自然语言修改，并生成下一版完整配套；
- 只返回唯一配套对象，无法守住正文边界时停止并说明缺口。

### 程序职责

- 只在 `draft_approved / package_pending` 合法状态准备输入；
- 重新校验 `approved_draft.json`、正文 JSON/Markdown 和当前版本绑定；
- 校验 AI 输出字段、数量、互异性、推荐项、发布正文字数和标签数量；
- create-only 保存 `package_vN.json`，旧版本不得覆盖；
- 用户确认时固定当前配套版本和选定标题，复用既有 `package_pending → package_approved`；
- 通过当前 Registry 与 Manifest 重新校验冻结客户位置并解析唯一输出目录；
- 调用唯一 `vault_save` Runtime，一次预检、create-only 写入并回读两份 Markdown；
- 两份都成功才进入既有 `saved` 状态；失败保留已确认版本并可在同一 Run 重试；
- 保存结果始终保持 `publish_status=not_requested`，不调用发布能力。

## 保存合同

### 纯口播稿

只写 `approved_draft` 绑定的最终正文原文，不含 frontmatter、标题、发布正文、标签、来源或内部状态。配套生成、选择和保存均不得改变一个字符。

### 配套文案

只写选定封面标题、选定发布标题、50—100 字发布正文和 5 个标签，不重复正文。

两个目标必须位于 Manifest 授权的输出根和模板目录下；目标在写入前一起检查，任一已存在或路径越界即停止。两份写入并回读一致后才成功；不执行 Git、提交、推送、同步、上传、数字人或发布。

## 依赖工具

- 创建期：完整回读本设计卡后显式调用 `skill-creator`；
- 运行期：只接收 `content-slim` 准备的已确认正文、可选当前配套和本次修改意见；
- 确定性依赖：现有 `run_store`、`state_machine`、`schema_validation`、`error_reporting`，以及本阶段唯一允许新增的 `vault_save`；
- 旧标题、分发、保存 Skill 的运行依赖为 0。

## 禁止访问范围

- Registry、Manifest、03/04/05、整个 Vault、参考全文、历史稿、网络和其他客户资料；
- 已确认正文之外的旧正文版本；
- 旧 V1 Packet、标题、分发、保存、Review 和 trusted loader 运行链；
- 客户 RC、Host、Git、远端、构建、安装、上传和发布平台；
- 任何由 AI 临时生成的执行程序。

## 错误与返修

- 正文未确认、版本错绑、正文 JSON/Markdown 不一致或正文被改动时停止，不生成配套；
- AI 输出字段、数量、推荐项、字数或标签不合法时拒绝保存，保留当前 Run 和已有版本；
- “需要修改”必须带具体意见，在同一 Run 基于最新配套生成下一版，不覆盖旧版；
- “确认并保存”只确认用户实际看到的最新版本；用户可选当前其他标题，不能提供候选外标题；
- Registry 重绑、Manifest 无效、输出目录越界、目标重名或任一写入/回读失败时，不报告保存完成；
- 保存重试只复用已确认的正文与配套，不重新生成内容；
- 任一失败不修改正文、不发布、不进入 P6。

## 最小示例

1. 当前 Run 为 `draft_approved`，程序回读 `approved_draft.json` 和对应正文双文件；
2. `$content-publish-pack` 只根据这份正文生成 2 个封面标题、3 个发布标题、推荐项、一段发布正文和 5 个标签；
3. 程序保存 `package_v1.json` 并完整展示；
4. 用户说“第二个发布标题太抽象，改得更具体”，同一 Run 生成 `package_v2.json`，旧版保留；
5. 用户确认并默认采用推荐标题；程序固定 `package_v2`，一次 create-only 保存纯口播稿和配套文案；
6. 两份文件回读一致后状态为 `saved`，结果保持未发布，P5 到此停止。

## P5 验收标准

- 本设计卡先于 Skill 创建，已完整回读并通过 Master SPEC/PHASE-P5 边界校验；
- `skill-creator` 初始化命令、输出、源文件哈希和设计卡哈希可回读；
- P5 只新增 `content-publish-pack` 一个 Skill，新增 Runtime 模块不超过一个 `vault_save.py`；
- 配套正式输入只含已确认正文，修改动作不创建第二层 Pack；
- 输出固定为 2 个封面标题、3 个发布标题、各 1 个推荐、50—100 字发布正文和 5 个标签；
- 配套修改留在同一 Run，旧版本可回读；
- 生成和修改配套不会改变已确认正文；
- 最终确认不增加第四个真人停点，同一确认动作直接保存；
- 两个目标一起预检、create-only 写入并分别回读，半套文件不报告成功；
- 保存后为未发布，不调用 Git、推送、同步、上传或发布；
- 新增状态、Reviewer、对外稳定操作和旧 V1 运行调用均为 0；
- 一条真实黑盒 P5 路径先通过，再通过 P5 聚焦测试和必要 P1—P4 回归；
- P5 结束时只记录 `P5 completed / review pending`，不得自行宣布 Gate P5 PASS 或进入 P6。

## 新增项的消费者与替代关系

| 新增项 | 保护的业务结果 | 消费者 | 替代的旧步骤 | 不增加时的可复现问题 | 为何不能并入其他职责 |
| --- | --- | --- | --- | --- | --- |
| `content-publish-pack` | 一次获得完整标题、发布正文和标签 | 用户与保存编排 | 旧标题 Skill、分发 Skill 和轻量 Reviewer 往返 | 用户要跨两个阶段拼配套，或正文未确认就生成配套 | 配套生成是独立语义职责，不能并入 Writer 或确定性保存 |
| `package_vN.json` | 同 Run 配套修改可回读且不覆盖 | 用户、最终确认和保存 | 多份标题/分发候选 Artifact | 修改会覆盖旧候选，保存无法确定用户看到哪一版 | 一份对象正好承载 Master SPEC 规定的完整配套输出 |
| `approved_package.json` | 保存复用用户实际确认的配套和标题选择 | `vault_save` 与保存失败重试 | 额外保存确认和旧最终收据链 | 保存失败后无法证明重试的是同一确认版本 | 并入版本会把 AI 候选冒充真人选择；固定收据不新增 Gate |
| `vault_save.py` | 两份文件都成功才报告保存完成 | `content-slim` | 旧 `content-save` 与 Git/发布耦合 | 第二份失败时可能留下半套并错误报告成功 | 双文件事务与路径安全是确定性职责，不能交给 AI Skill |
